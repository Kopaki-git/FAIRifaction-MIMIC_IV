# AGENTS.md

## Purpose

This file is the handoff document for Codex or any other coding agent working on this repository without prior conversational context.

Read this file together with `README.md` before changing code, data transformations, semantic mappings, or project structure.

The repository is a **FAIR Data Engineering course project** based on a bounded extract of the **MIMIC-IV Clinical Database Demo v2.2**. The project goal is not to build a predictive clinical model. The goal is to incrementally FAIRify a small real clinical dataset, with the main technical focus on **semantic interoperability**.

## Core project idea

MIMIC-IV is already strong in several FAIR dimensions. It is documented, versioned, licensed, structured, and distributed through PhysioNet. The project therefore should not be framed as "repairing a non-FAIR dataset."

The main problem studied here is this:

> MIMIC ICU observations are well structured inside the MIMIC ecosystem, but important meaning is encoded through MIMIC-local identifiers, unit strings, relational conventions, and documentation. The project will preserve those source semantics while adding explicit machine-actionable relations and mappings to shared vocabularies.

Do not describe semantic interoperability as a machine "understanding" clinical concepts in a human sense. Operationally, the goal is to encode enough explicit structure that software can identify, compare, query, validate, and combine data without bespoke MIMIC-specific interpretation.

## Canonical extraction rule

The project selects exactly three MIMIC ICU measurement types:

| itemid | Source label | Abbreviation | Source unit |
|---:|---|---|---|
| 220045 | Heart Rate | HR | bpm |
| 220210 | Respiratory Rate | RR | insp/min |
| 220277 | O2 saturation pulseoxymetry | SpO2 | % |

For each ICU stay, include observations with:

```text
charttime >= intime
and
charttime < intime + 4 hours
```

In interval notation:

```text
[ICU intime, ICU intime + 4 hours)
```

The four-hour boundary is an **engineering scope choice**, not a clinical threshold or clinical hypothesis.

Do not rewrite documentation to imply that the first four hours are physiologically or prognostically special.

The reason for using a temporal rule rather than randomly sampling approximately 2,500 records is that the resulting subset has a coherent semantic interpretation: all selected vital-sign observations from the first four hours of each ICU stay.

## Canonical CSV schema

The output has exactly these nine fields at the current stage:

```text
subject_id
hadm_id
stay_id
charttime
itemid
measurement_label
valuenum
valueuom
warning
```

Meaning:

- `subject_id`: MIMIC-local patient identifier.
- `hadm_id`: MIMIC-local hospital-admission identifier.
- `stay_id`: MIMIC-local ICU-stay identifier.
- `charttime`: deidentified charted time associated with the observation.
- `itemid`: MIMIC-local measurement identifier.
- `measurement_label`: label joined from `d_items`.
- `valuenum`: numeric measurement value.
- `valueuom`: source unit representation.
- `warning`: source warning flag.

Do not drop `itemid` after introducing standard terminology mappings. The local source identifier must remain available for provenance and traceability.

## Important temporal semantics

Use `charttime` for the observation timestamp in the extraction.

Use `icustays.intime` as the start of the ICU stay.

Do **not** use `storetime` to define the first-four-hour interval. `storetime` represents entry/storage/validation timing rather than the charted observation time relevant to the extraction rule.

MIMIC timestamps are shifted for deidentification. Dates such as year 2180 are expected and are not real calendar dates. Relative temporal intervals remain useful.

Do not "correct" future-looking dates.

## Semantic model: provisional structure

The likely conceptual chain is:

```text
Patient
  -> Hospital admission
      -> ICU stay
          -> Clinical observation
              -> observed property
              -> numeric value
              -> unit
              -> observation time
              -> optional warning/source-quality information
```

Provisional semantic types:

- Patient / subject
- Hospital admission
- ICU stay / encounter
- Clinical observation
- Observable / measurement type
- Numeric quantity / value
- Unit
- Observation time
- Warning / quality indicator

These are **conceptual requirements**, not commitments to specific ontology classes.

Do not prematurely hard-code ontology terms merely because they look plausible.

## Competency questions

Use competency questions to drive the semantic model. Current candidates are:

1. What vital-sign observations belong to a particular ICU stay?
2. Which patient and hospital admission does a given ICU observation belong to?
3. What physiological property does an observation measure?
4. What numeric value and unit does an observation have?
5. When was the observation charted?
6. Can all heart-rate observations be retrieved without knowing the MIMIC `itemid`?
7. Which observations have a warning flag?

When adding RDF or ontology mappings, verify that the resulting graph can answer these questions cleanly.

## Semantic interoperability: precise interpretation

Do not equate a human-readable label with a shared semantic concept.

Example:

```text
itemid = 220045
label = "Heart Rate"
```

This is already understandable to a human familiar with MIMIC, but `"Heart Rate"` is still a text label and `220045` is still a MIMIC-local code.

A later semantic mapping may say, conceptually:

```text
mimic:220045  ->  shared concept for heart rate
```

The purpose of the shared identifier is not mystical machine comprehension. Its value comes from being part of an agreed formal vocabulary with machine-readable identifiers and relationships.

This enables software to make operations such as:

- identify observations that represent the same physiological property across datasets;
- query all observations of a broader class;
- validate unit or property relationships;
- follow explicit links without parsing labels or bespoke documentation.

## Mapping policy

When mapping MIMIC-local concepts to shared vocabularies:

1. preserve the original local MIMIC concept;
2. add the external mapping separately;
3. document why the mapping is justified;
4. distinguish exact equivalence from broader/narrower or approximate mappings;
5. avoid silently replacing source meaning with a standardized interpretation.

This is especially important for SpO2, where a broad oxygen-saturation concept and a pulse-oximetry-specific concept may not be interchangeable.

Do not choose `owl:sameAs`, `skos:exactMatch`, or similar predicates casually. Mapping strength is itself a semantic claim.

## Existing MIMIC-to-FHIR work

Important prior work exists converting MIMIC-IV to FHIR.

FHIR is a healthcare data-exchange standard using resources such as Patient, Encounter, and Observation. Existing MIMIC-to-FHIR work already expresses much of the patient/encounter/observation structure.

Therefore:

- do not claim novelty for converting rows into generic Observation/Encounter structures;
- treat MIMIC-FHIR as relevant prior art and a useful modelling reference;
- focus project contribution on semantic FAIRification of the bounded resource, including terminology alignment, explicit provenance/metadata, Linked Data identifiers, and publication.

A key remaining semantic boundary is that ICU `chartevents` may retain MIMIC-local measurement and unit systems even inside a FHIR representation.

## Potential external linking target

A natural later dataset for linking is the **MIMIC-IV-ED Demo v2.2**.

The ED demo shares the demonstration patient population and includes vital-sign data such as heart rate, respiratory rate, and oxygen saturation.

A useful later interoperability question is:

> Can ED and ICU observations of the same physiological property be queried together using shared semantic identifiers rather than source-specific codes?

Cross-dataset integration is optional/bonus scope. Do not prioritize it over completing the core course requirements.

## Coding style and implementation preferences

This is a small course repository. Prefer straightforward, inspectable code over infrastructure-heavy abstractions.

Guidelines:

- use readable Python and pandas for tabular preprocessing unless another tool is specifically justified;
- keep notebooks focused and narratively documented;
- avoid unnecessary classes, dependency injection, framework scaffolding, or generic pipeline systems;
- keep transformation logic deterministic;
- add assertions for important invariants;
- prefer stable sorting before writing canonical tabular outputs;
- keep generated semantic artefacts reproducible from tracked code/configuration;
- avoid modifying source data in place;
- do not mix exploratory code with silently authoritative transformations;
- document project decisions close to the code that implements them.

## Notebook policy

The notebook is appropriate here because the derivation decision itself is part of what must be understandable and reproducible.

For exploratory and modelling stages, prefer a notebook when visual inspection, comparison, or explanation is integral to the work.

If a transformation later becomes repetitive, complex, or needs to run unattended, factor stable logic into `src/` and let a notebook call it rather than duplicating logic.

Do not refactor the current extraction notebook into a production pipeline merely for architectural cleanliness.

## Claims discipline

This repository should make bounded claims.

Acceptable:

> The project adds explicit semantic mappings to a bounded MIMIC-IV Demo vital-sign resource.

Acceptable:

> The four-hour window was chosen as an engineering scope boundary.

Not acceptable without evidence:

> The first four ICU hours are the clinically most important period.

Not acceptable:

> MIMIC-IV is non-FAIR.

Better:

> MIMIC-IV already has strong FAIR properties, while this project targets remaining semantic-interoperability and machine-actionability gaps in a bounded extract.

Not acceptable:

> Converting this dataset to RDF solves interoperability.

Better:

> RDF provides a representation mechanism; interoperability depends on the semantic model, identifiers, mappings, vocabulary reuse, and how clearly relations are defined.
