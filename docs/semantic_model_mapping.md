# MIMIC-IV Demo FAIRification — Canonical Semantic Model Specification

**Status:** Canonical, globally audited semantic specification for the current project scope.  
**Audit checkpoint:** 2026-10-13.  
**Dataset:** MIMIC-IV Clinical Database Demo v2.2.  
**Bounded resource:** Heart rate, respiratory rate, and pulse-oximetry observations from the first four hours of represented ICU stays.  
**Architecture:** HL7 FHIR R4 clinical structure plus shared terminologies where FHIR expects them.  
**Baseline for FAIRification claims:** MIMIC-IV plus interoperability already provided by the published MIMIC-FHIR mapping.

This document is the single canonical semantic-model specification for the repository. It defines the approved clinical-semantic model and terminology mappings. It is **not** an executable RDF transformation, FHIR Implementation Guide, provenance record, SHACL specification, or publication/URI configuration.

The former root-level `Semantic_data_model.json` was an RDFTransform implementation tied to an obsolete single-CSV/SOSA-QUDT model. It is intentionally removed rather than reconstructed. Its history remains available through Git.

---

## 1. Scope and FAIRification objective

MIMIC-IV is already strongly structured, documented, versioned, and reusable within the MIMIC ecosystem. The project therefore does not treat RDF conversion itself as the contribution.

The semantic objective is:

> Make clinically important distinctions machine-actionable using shared representations where defensible, while preserving source meaning and avoiding assertions stronger than MIMIC supports.

Every retained modelling choice should produce a defensible interoperability gain over the source and, where relevant, over MIMIC-FHIR. Existing FHIR structure that MIMIC-FHIR already provides is treated as baseline rather than claimed as a new FAIRification contribution.

The project scope remains deliberately narrow. It does not attempt to FAIRify all of MIMIC-IV or every field available in the source tables.

## 3. Modelling principles

### 3.1 Source identifiers are not graph identity

`subject_id`, `hadm_id`, `stay_id`, `itemid`, and other MIMIC identifiers remain local source identifiers attached to resources or codings. They are not treated as globally meaningful resource identities.

Exact resource URI construction is deferred to publication/implementation design.

### 3.2 Preserve source meaning, then standardize

Where a defensible standard mapping exists, the model retains the source representation and adds the standard representation rather than erasing the local source semantics.

Examples include:

- MIMIC `itemid` coding plus LOINC;
- source `valueuom` text plus UCUM;
- source ICD coding plus canonical ICD-9-CM or ICD-10-CM coding;
- verbatim `admission_type` plus a standard FHIR priority only where that mapping is defensible.

### 3.3 Do not force completeness

A source value is not mapped to a standard concept merely because a vaguely related concept exists. Inexact mappings remain absent from instance data unless a later mapping artifact such as FHIR `ConceptMap` is explicitly justified.

### 3.4 Not every source field belongs in the FAIR graph

The canonical derived resource is the reproducible source object, not a promise that every column becomes RDF/FHIR semantics. A field is represented only when it contributes to the scoped interoperable meaning or is intentionally preserved for source fidelity.

### 3.5 FHIR structure is not itself the claimed contribution

FHIR R4 provides the structural clinical model. Shared terminologies are used where FHIR expects them. MIMIC-FHIR is the relevant interoperability baseline, so basic conversion into `Observation`, `Encounter`, `Patient`, and related FHIR structures is not presented as novel FAIRification.

## 5. Observation model

### 5.1 Observation grain

Each retained source row for heart rate, respiratory rate, or SpO₂ becomes one FHIR R4 `Observation`.

No aggregation, composite-observation layer, or separate measurement-event resource is introduced.

### 5.2 Status

`Observation.status = final`.

This follows the MIMIC-FHIR conversion policy. It is a transformation policy, not a value derived from a MIMIC source column and not a new FAIRification contribution.

### 5.3 Vital Signs profile semantics

The observations are modelled according to the FHIR R4 Vital Signs profile semantics:

- category `vital-signs`;
- Patient subject;
- measurement time;
- numeric quantity;
- required LOINC coding;
- UCUM-computable unit.

An explicit `meta.profile` assertion is deferred until generated resources pass FHIR validation.

### 5.4 Observation time

`Observation.effectiveDateTime = charttime`.

MIMIC timestamps are deidentified/shifted. The semantic model preserves the represented temporal relationships; it does not reinterpret shifted calendar dates as real-world dates.

### 5.5 Patient and encounter references

`Observation.subject` references the Patient identified locally by `subject_id`.

`Observation.encounter` references the ICU Encounter identified locally by `stay_id`.

The MIMIC identifiers are represented as local FHIR identifiers, not as global graph identity.

### 5.6 Warning flag

The source `warning` value is preserved through a narrow project-defined `Observation` extension:

- `0 → valueBoolean false`;
- `1 → valueBoolean true`.

The extension means only that a warning for the source observation was manually documented by the care provider. It is **not** reinterpreted as FHIR `Observation.interpretation`, clinical abnormality, or invalidity.

The extension's canonical URL is deferred to project namespace/publication design.

## 6. Measurement terminology and units

### 6.1 Observation.code

Each `Observation.code` preserves the MIMIC item coding and adds standard LOINC coding.

| MIMIC itemid | Source label | Standard coding |
|---:|---|---|
| 220045 | Heart Rate | LOINC `8867-4` — Heart rate |
| 220210 | Respiratory Rate | LOINC `9279-1` — Respiratory rate |
| 220277 | O2 saturation pulseoxymetry | LOINC `2708-6` plus `59408-5` |

For SpO₂, FHIR R4 Vital Signs uses `2708-6` as the required oxygen-saturation code and permits `59408-5` as the additional pulse-oximetry-specific coding. Both are therefore retained.

LOINC system:

`http://loinc.org`

The MIMIC item CodeSystem URI is an implementation/publication decision still to be finalized.

### 6.2 Quantity and UCUM

The source numeric value is represented as `Observation.valueQuantity.value = valuenum`.

The source unit string is retained verbatim in `Quantity.unit`, while `Quantity.system` and `Quantity.code` provide UCUM normalization:

| Measurement | Source `valueuom` retained in `unit` | UCUM system | UCUM code |
|---|---|---|---|
| Heart rate | `bpm` | `http://unitsofmeasure.org` | `/min` |
| Respiratory rate | `insp/min` | `http://unitsofmeasure.org` | `/min` |
| SpO₂ | `%` | `http://unitsofmeasure.org` | `%` |

QUDT is not used because it adds no independently justified value to the chosen FHIR representation.

Whether UCUM normalization is a novel contribution over the MIMIC-FHIR baseline remains to be checked before it is claimed as such in the final report.

## 7. Patient and encounter hierarchy

### 7.1 Patient

One FHIR `Patient` resource represents each MIMIC patient in scope.

`subject_id` is preserved as a local `Patient.identifier` value. Its exact `Identifier.system` URI is deferred.

### 7.2 ICU Encounter

Each represented ICU stay becomes a FHIR `Encounter`:

- local identifier value: `stay_id`;
- `status = finished`;
- `class = ACUTE`;
- `subject = Patient`;
- `period.start = icu_stays.intime`;
- `period.end = icu_stays.outtime`;
- `partOf = Hospital Encounter`.

The class coding is:

- system: `http://terminology.hl7.org/CodeSystem/v3-ActCode`
- code: `ACUTE`

This follows the MIMIC-FHIR baseline and is not claimed as a new contribution.

### 7.3 Hospital Encounter

Each represented `hadm_id` becomes a FHIR `Encounter` representing the full hospitalization:

- local identifier value: `hadm_id`;
- `status = finished`;
- `class = IMP`;
- `subject = Patient`;
- `period.start = admittime`;
- `period.end = dischtime`.

The class coding is:

- system: `http://terminology.hl7.org/CodeSystem/v3-ActCode`
- code: `IMP`

The hospital Encounter represents the full hospitalization rather than the admission route. Emergency, observation, or same-day source labels are therefore not used as the Encounter class.

## 8. Hospital admission semantics

### 8.1 Preserve admission_type verbatim

The source `admission_type` string is preserved on the Hospital Encounter through a narrow project-defined extension with `valueString`.

Examples include:

- `EW EMER.`
- `DIRECT EMER.`
- `URGENT`
- `ELECTIVE`
- `OBSERVATION ADMIT`
- `SURGICAL SAME DAY ADMISSION`

The extension is source preservation. It does not assert that all six values form one standard FHIR terminology.

Its canonical URL is deferred.

### 8.2 Standardized Encounter.priority where defensible

MIMIC documents `admission_type` as useful for classifying admission urgency. FHIR separates that urgency from the broad Encounter class.

The approved mappings are:

| MIMIC admission_type | FHIR `Encounter.priority` code |
|---|---|
| `ELECTIVE` | `EL` — elective |
| `URGENT` | `UR` — urgent |
| `EW EMER.` | `EM` — emergency |
| `DIRECT EMER.` | `EM` — emergency |
| `OBSERVATION ADMIT` | no standardized priority asserted |
| `SURGICAL SAME DAY ADMISSION` | no standardized priority asserted |

Priority code system:

`http://terminology.hl7.org/CodeSystem/v3-ActPriority`

The two unmapped values remain available through the verbatim source extension. No speculative priority is introduced.

## 9. Time-resolved care-unit model

### 9.1 Encounter.location rather than first_careunit

The model does not use the old lossy `first_careunit` representation.

Each validated care-unit interval inside an ICU stay becomes one repeated `Encounter.location` backbone element:

- `Encounter.location.period.start = transfers.intime`;
- `Encounter.location.period.end = transfers.outtime`;
- `Encounter.location.location` references a reusable FHIR `Location` representing the care-unit kind.

Each distinct MIMIC care-unit label is represented as a reusable `Location` with:

- `Location.mode = kind`;
- `Location.name = careunit` verbatim.

This preserves time-resolved within-ICU care-setting history rather than attaching one first-care-unit label to the entire stay.

### 9.2 HL7 Location.type mappings and extensible-binding policy

FHIR R4 `Location.type` is a `CodeableConcept` with an **extensible binding** to `ServiceDeliveryLocationRoleType`.

Under an extensible binding, if a code in the bound value set applies to the concept being represented, a conformant instance must include a coding from that value set. If the closest applicable bound concept is broader than the intended meaning, the closest applicable bound code is still used. Because `Location.type` is a `CodeableConcept`, a more specific coding from another terminology may additionally be supplied, but it does not replace the applicable bound coding.

This explains two deliberate features of the care-unit model:

- The HL7 mappings are sometimes **lossy classifications rather than equivalence mappings**. For example, `Trauma SICU`, `Cardiac Vascular Intensive Care Unit`, and `Medical/Surgical Intensive Care Unit` all receive the broader bound role `ICU`. Their source specificity is not discarded: the verbatim MIMIC `careunit` remains represented by the `Location`.
- SNOMED CT is therefore used as an **additional coding**, not as a replacement for the HL7 coding, where it provides defensible extra specificity. For MICU and SICU, the bound HL7 role `ICU` is retained and the more specific SNOMED CT concept is added to the same `CodeableConcept`. Where no sufficiently exact SNOMED concept was established, no additional SNOMED coding is asserted.

The approved closest-applicable bound roles are:

| MIMIC careunit | Closest applicable HL7 role code(s) | Specificity relative to source |
|---|---|---|
| Medical Intensive Care Unit (MICU) | `ICU` | broader; supplemented by SNOMED CT |
| Surgical Intensive Care Unit (SICU) | `ICU` | broader; supplemented by SNOMED CT |
| Medical/Surgical Intensive Care Unit (MICU/SICU) | `ICU` | broader |
| Trauma SICU (TSICU) | `ICU` | broader |
| Neuro Surgical Intensive Care Unit (Neuro SICU) | `ICU` and `NS` as separate `Location.type` values | combined broader role facets |
| Neuro Stepdown | `HU` | broader |
| Cardiac Vascular Intensive Care Unit (CVICU) | `ICU` | broader |
| Coronary Care Unit (CCU) | `CCU` | direct |
| Neuro Intermediate | `HU` | broader |

Bound code system:

`http://terminology.hl7.org/CodeSystem/v3-RoleCode`

Relevant meanings:

- `ICU` — Intensive care unit;
- `NS` — Neurosurgery unit;
- `HU` — Hospital unit;
- `CCU` — Coronary care unit.

The authoritative FHIR rule behind this policy is the R4 extensible-binding rule: when an applicable bound concept is broader than the intended meaning, the closest applicable code from the bound value set is still used; a more specific external coding may additionally be included in a `CodeableConcept`, but cannot replace the applicable bound coding.

### 9.3 Direct SNOMED CT co-coding

Following the extensible-binding policy above, SNOMED CT is added as a second coding only where it supplies a defensible more-specific representation of the same intended care-unit concept.

| MIMIC careunit | SNOMED CT |
|---|---|
| Medical Intensive Care Unit (MICU) | `441994008` — Medical intensive care unit |
| Surgical Intensive Care Unit (SICU) | `418433008` — Surgical intensive care unit |

No direct SNOMED co-coding is asserted for the remaining seven labels.

Potential broader or inexact relationships may later be documented through a FHIR `ConceptMap`, but they must not be represented as equivalent instance codings merely to achieve full mapping coverage.

A US-extension trauma-ICU concept is also not introduced unless use of national SNOMED extensions becomes an explicit project terminology policy.

## 10. Diagnosis model

### 10.1 Selected diagnosis

For each represented Hospital Encounter, the project retains only the `diagnoses_icd` row with `seq_num = 1`.

This is described as the **first-ranked encounter diagnosis**.

It is not described as:

- the biological cause of admission;
- the primary clinical diagnosis;
- a diagnosis necessarily known during the first four ICU hours.

MIMIC describes these as billed diagnoses and `seq_num` as their priority ordering.

### 10.2 FHIR representation

The Hospital Encounter contains one `Encounter.diagnosis` backbone element:

- `condition → Condition`;
- `use = billing`;
- `rank = 1`.

Diagnosis role coding:

- system: `http://terminology.hl7.org/CodeSystem/diagnosis-role`
- code: `billing`

The referenced `Condition` contains:

- `subject → Patient`;
- `encounter → Hospital Encounter`;
- `category = encounter-diagnosis`;
- `code → CodeableConcept`.

Condition category coding:

- system: `http://terminology.hl7.org/CodeSystem/condition-category`
- code: `encounter-diagnosis`

No longitudinal problem-list semantics are implied.

### 10.3 Original and canonical ICD coding

`Condition.code` preserves an original MIMIC-compatible ICD coding and adds the corresponding canonical ICD coding.

The source coding retains:

- raw `icd_code`;
- `long_title` as display;
- the distinction given by `icd_version`.

Canonical systems:

- ICD-9-CM: `http://hl7.org/fhir/sid/icd-9-cm`
- ICD-10-CM: `http://hl7.org/fhir/sid/icd-10-cm`

Canonical code formatting inserts the standard decimal while preserving the source code itself in the original coding.

For example:

`41401 → 414.01`

Historical ICD-10-CM codes are retained as historically valid source concepts rather than silently upgraded to later replacement codes. In particular, the selected cohort includes historically valid `S0262XA` and `T814XXA`, which must not be modernized into different concepts.

No `Coding.version` is asserted because the source does not identify a specific annual code-system edition. Historical validity belongs in provenance/documentation.

## 11. Deliberate omissions from the semantic graph

### 11.1 careunit_intervals.transfer_id

`transfer_id` remains in the canonical derived source table but is not represented in the semantic graph.

It identifies a MIMIC physical-location record. The scoped FHIR model intentionally represents the time-bounded care-setting history and reusable care-unit kinds rather than preserving every source record identity as a clinical semantic entity.

It may remain useful for derivation/provenance traceability, but it is not promoted into the clinical model.

### 11.2 careunit_intervals.eventtype

`eventtype` also remains in the canonical derived source table but is omitted from the current semantic graph.

Within this bounded resource it distinguishes whether the first ICU interval begins as an `admit` or a `transfer`; subsequent selected intervals are transfers. That distinction is real but is not required to interpret the vital signs, ICU Encounter, or time-resolved care-unit history in the current scope.

It should be reconsidered only if direct-to-ICU versus intra-hospital transfer becomes an explicit competency question or reuse goal.

### 11.3 No invented encounter/location resources for transfers

`transfer_id` is not promoted to a FHIR Encounter.

The transfer intervals are represented through `Encounter.location`, with their time periods and referenced care-unit Locations.

## 12. FAIRification contribution versus baseline

The comparison baseline is not raw CSV alone. It is MIMIC-IV plus interoperability already available through MIMIC-FHIR.

### 12.1 Baseline / conformance, not claimed as new contribution

The following are primarily inherited FHIR structure or conversion policy:

- MIMIC charted events represented as FHIR `Observation`;
- Patient references;
- ICU Encounter references;
- hospital/ICU Encounter hierarchy through `partOf`;
- Observation timestamp in `effectiveDateTime`;
- quantity structure;
- Encounter `status = finished`;
- ICU Encounter `class = ACUTE`;
- core FHIR resource/cardinality conformance;
- preservation of `warning` through a local extension;
- verbatim preservation of `admission_type` through a local extension.

### 12.2 Intended semantic FAIRification gains

The audited model adds or strengthens:

1. **Shared vital-sign terminology:** MIMIC item codes are aligned with the FHIR-required LOINC concepts while the local coding remains traceable.
2. **Time-resolved care-setting semantics:** care-unit changes are represented through repeated, time-bounded `Encounter.location` entries instead of a single first-care-unit label.
3. **Standard care-setting roles:** FHIR-bound HL7 location-role codes are added, with SNOMED CT only where a direct extra specificity is defensible.
4. **Hospital encounter classification and urgency separation:** the full hospitalization is consistently classed as `IMP`, while source admission urgency is exposed through `Encounter.priority` only for defensible mappings.
5. **Canonical diagnosis terminology:** first-ranked billed diagnoses retain the source coding and add canonical ICD-9-CM/ICD-10-CM identity without rewriting historical codes.
6. **Explicit diagnosis role and rank:** the selected diagnosis is represented as an encounter diagnosis with `use = billing` and `rank = 1`, avoiding the misleading phrase “primary clinical diagnosis.”

UCUM normalization is part of the model, but its novelty over MIMIC-FHIR must be verified before the final report claims it as an additional FAIRification contribution.

## 13. Deferred implementation and publication decisions

The clinical-semantic model is frozen, but the following remain intentionally unresolved because they belong to implementation, publication, or provenance rather than the core model:

- exact resource URI patterns;
- exact `Identifier.system` URIs for MIMIC local identifiers;
- exact URI/reuse strategy for MIMIC local CodeSystems;
- canonical URLs and formal `StructureDefinition` resources for the warning and admission-type extensions;
- whether to publish a care-unit `ConceptMap` for broader/inexact mappings;
- exact FHIR-RDF serialization mechanics;
- RDF transformation technology and executable mapping artifacts;
- validation tooling and validator-confirmed `meta.profile` assertions;
- SHACL constraints;
- dataset/derivation provenance and mapping-justification documentation;
- final publication infrastructure and dereferenceable project namespaces.

These choices must not be silently baked into the semantic specification merely to make an implementation convenient.
